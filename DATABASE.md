# Database

PostgreSQL is the authoritative store. `packages/db/migrations` contains ordered SQL migrations, applied transactionally under an advisory lock by `npm run db:migrate`. Migration names are recorded in `schema_migrations`. Do not edit an applied migration; add another migration.

Better Auth owns the core `user`, `session`, `account` and `verification` schema. These use the column naming expected by the installed Better Auth adapter and UUID defaults. The application adds a validated IANA `timezone` preference to `user`; scheduled timestamps remain `timestamptz` UTC instants. Application-owned relations use snake_case names and UUID primary keys.

Organization membership and client membership are separate. Organization owners/admins can access all clients in their organization. Other roles require an explicit client membership. Client resources carry both `organization_id` and `client_id`. Composite foreign keys prevent an account, target, credential or approval from referencing a client in another organization.

`member_invitations` stores only a SHA-256 token hash, the invited email, role, expiry and lifecycle status. `member_invitation_clients` scopes non-admin invitations to clients in the same organization through composite foreign keys. Accepting an invitation creates organization and client memberships in one transaction.

`posts` owns base content and revision; `post_targets` owns network caption, media IDs and independent delivery status. Immutable `post_versions` snapshots bind approvals to a revision. `publish_jobs` is the durable outbox, with one row and one stable idempotency key per target. `publish_attempts` records outcomes and safe provider error codes. `mock_receipts` and `provider_receipts` persist deduplication across worker restarts. Provider receipts have a composite foreign key to the same organization/client/idempotency key as their publish job.

`publish_reconciliation_jobs` records automatic and administrator-triggered checks for `META_DELIVERY_UNCERTAIN`. Each publish job has at most one reconciliation row. Composite tenant foreign keys prevent cross-client evidence, due indexes support worker claims, and matched remote IDs become ordinary provider receipts before the target is marked published. Ambiguous and exhausted not-found checks remain durable `UNRESOLVED` evidence.

Media bytes are stored in S3, never permanently in the web process. The browser uploads to a random client-scoped incoming key using a five-minute signed PUT URL. Completion verifies object size and content type before creating a durable `media_processing_jobs` outbox row. The worker validates actual bytes, fully decodes images or probes H.264 MP4 video, writes a JPEG preview, moves the accepted bytes to a separate ready key and records dimensions/duration. Failed assets retain a safe error code; invalid objects and uploads abandoned for more than one hour are deleted.

Media processing jobs are client scoped through a composite foreign key, retry transient failures up to three times and recover stale `RUNNING` rows after a worker interruption. Target media references are UUID arrays checked by application services and a database trigger: every reference must be a distinct, ready, non-deleted asset in the same organization/client. Mock receipts also carry organization/client scope enforced by foreign keys.

Approval requests freeze the remaining workflow steps, automation policy and post revision when created. Internal requests also store a named assignee, reminder schedule/counts and an expiry lifecycle. `approval_automation_deliveries` is a tenant-scoped email outbox for automatic reminders and administrator escalations, with bounded retry state and cancellation when a review closes or is reassigned. A database trigger rejects assignees without reviewer access to the same organization/client. Renewing an expired review creates a new request, leaving the expired record available as history. Editing a returned draft increments its revision and supersedes old pending requests; later workflow edits do not silently change reviews already in progress.

Calendar queries have scope/time indexes and load independent bounded time windows with server-side filters; status, reviewer queues and audit queries have scope indexes. The post library applies tenant scope, text search and platform/status/author filters in PostgreSQL, then pages in descending `(created_at,id)` order with an opaque cursor. Media and audit lists have bounded results.

`analytics_daily` and `post_metrics` retain raw provider values and normalized values alongside provider identity. Scope/date and latest-target-metric indexes support bounded dashboard queries. Account activity is summed by day, followers use the latest snapshot in the period, and top content uses the latest stored snapshot for targets published in the selected range. Do not interpret summed reach as unique people across networks.

`analytics_sync_jobs` is the durable analytics outbox. Partial unique indexes permit one profile job per account/day and one post job per target/day. A trigger rejects post work assigned to a different social account. Jobs recover from interrupted workers, retry transient failures three times and retain safe terminal error codes. Manual reconciliation resets the same rows instead of creating duplicate work. Disconnecting an account removes unfinished jobs; completed evidence follows the organization's retention policy.

`ai_generations` assigns an ID before the provider request and retains pending, completed and failed attempts. Each row records tenant/user/post scope, operation, provider/model/mode, input/output, the brand snapshot used, guardrail result, token usage, optional cost estimate and whether the suggestion was applied. Tenant-scoped history and single-generation endpoints expose these durable records; provider failures store safe error codes rather than response bodies.

`oauth_states` holds only hashed, expiring state values. Meta callback consumption deletes the row before external token exchange. `webhook_events` stores only signature-verified, account-mapped Meta changes and deduplicates them by a stable payload/account digest; the account composite foreign key preserves tenant scope.

`service_heartbeats` records non-secret service instance identity, release metadata and the latest worker observation. The worker refreshes its row every ten seconds and removes it during graceful shutdown; stale rows are retained briefly for diagnosis and removed after seven days. Tenant job detail remains in the scoped job tables and is exposed only to organization owners/admins.

`privacy_requests` is the durable, retryable ledger for personal and organization erasure. It keeps a one-way email hash and subject UUID as minimal evidence after authentication records are deleted; requester foreign keys become null. Active-request partial unique indexes prevent duplicate erasures. Invitation authors and authenticated approval-comment authors also become null during account erasure, while comments are anonymized by the worker.

The worker executes due account requests after 24 hours and organization requests after 72 hours. Organization cascades remove tenant rows while the worker removes S3 objects. Daily retention cleanup uses each organization's 30–3650 day policy for completed operational records and soft-deleted posts/media. Database and object deletion do not shorten external backup expiry; production backup retention must be aligned separately.

`api_keys` holds organization API keys for the `/api/v1` integration API. It stores only `key_hash` (SHA-256 hex of the raw key, unique index) and a short identifying `key_prefix` (`shk_live_` plus six characters); the raw key is never written to the database. Rows cascade with the organization; `created_by_user_id` and `revoked_by_user_id` become null when the user is erased. Revocation sets `revoked_at` instead of deleting the row, and each authenticated request refreshes `last_used_at`.

`025_api_idempotency.sql` adds nullable `posts.suggested_at`, `posts.pillar`, `posts.source` (1–100 characters) and `posts.media_urls` (JSON array of HTTPS URLs) for drafts uploaded through `/api/v1`. They are metadata only: `suggested_at` never fills `scheduled_at`, and `media_urls` never creates `media_assets`. The partial index `posts_api_sync_idx (organization_id, updated_at, id)` serves `GET /api/v1/posts`. `api_idempotency_keys` stores one row per `(organization_id, key)` (unique index) with the issuing `api_key_id` (null once that key row is deleted), the SHA-256 `request_hash`, `response_status`, `response_body` and `created_at`. Rows are written in the same transaction as the drafts they describe and cascade with the organization; they expire after 24 hours: a stored response is replayed only within that window (an older row for the same key is deleted in the request's transaction, so the key runs as a new request), and the worker's hourly cleanup deletes expired rows in batches of 1000 (`DELETE … WHERE id IN (SELECT … LIMIT n)`, at most 20 batches per run) through `api_idempotency_keys_created_idx`. No schema change was needed.

`026_client_external_ref.sql` adds nullable `clients.external_ref`, the client's ID in an integrated tool such as Growth Engine (e.g. `mmi`, `viba-team`), returned by `GET /api/v1/clients`. A CHECK limits it to 1–64 lowercase letters, digits and hyphens (`^[a-z0-9-]{1,64}$`), and the partial unique index `clients_external_ref_unique (organization_id, external_ref) WHERE external_ref IS NOT NULL` keeps it unique within an organization while other organizations may reuse the value. A soft-deleted client keeps its value, so it stays reserved until it is cleared or the row is removed. Only owners/admins change it, and each change is audited with the old and new value. The migration only adds a nullable column and an index, so existing rows are unaffected. `GET /api/v1/clients/{id}/metrics` reads the existing `analytics_daily` and `post_metrics` tables through the `010_analytics_queries.sql` indexes and needs no schema change.

`027_brand_profile_sync.sql` adds nullable columns to `brand_profiles` for the brand profile synced from Growth Engine by `PUT /api/v1/clients/{id}/brand-profile`: `synced_profile` (jsonb: `voice`, `required_phrases`, `forbidden_phrases`, `required_disclaimer`, `pillars`), `synced_at`, `synced_source` (`growth_engine`), `synced_by_api_key_id` (references `api_keys`, null once that key row is deleted) and `synced_hash` (SHA-256 of the normalized profile, used for idempotency). Growth Engine owns these columns; the existing `profile` column stays the local supplement edited in Social Hub. The API never writes `profile` or `updated_at`, and the Social Hub save path never writes the `synced_*` columns. The migration only adds nullable columns, so existing rows and `profile` are unaffected.

`028_webhooks.sql` adds the outgoing webhooks of `/api/v1`. `webhook_endpoints` holds the organization's endpoints: an HTTPS `url` (CHECK `^https://`, at most 2048 characters), `secret_ciphertext` (the signing secret encrypted with the application encryption key; the raw secret is never stored), a short `secret_prefix`, the subscribed `events` (a non-empty subset of `post.approved`, `post.changes_requested`, `post.published`, `post.failed`), `created_by_user_id` and `revoked_by_user_id` (null after user erasure), `secret_rotated_at` and `revoked_at` (revocation keeps the row). Rows cascade with the organization; the partial index `webhook_endpoints_active_idx` serves the active-endpoint lookup during event capture. `webhook_deliveries` is the delivery outbox: a unique `event_id` per delivery, `organization_id`, `client_id` and `endpoint_id` (composite tenant foreign keys to `clients` and `webhook_endpoints`, cascading), `event_type`, the `payload` JSON (identifiers, statuses and error codes only), and the shared outbox fields `status` (`PENDING`/`RUNNING`/`RETRY`/`DONE`/`DEAD`), `attempts` (0–12), `run_at`, `last_error` (a short code), `last_status_code`, `started_at` and `completed_at`. Rows are inserted in the same transaction as the post state change; `webhook_deliveries_due_idx` serves the worker's `FOR UPDATE SKIP LOCKED` claim and the organization/status index serves Operations. Daily retention removes `DONE` and `DEAD` deliveries older than the organization's retention period. The migration only creates new tables.
